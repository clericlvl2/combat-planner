# ADR-002 — State: Svelte 5 runes + a thin store layer

Status: **Accepted** (2026-06-28).

**Decision.** Model reactive combat state with `$state` / `$derived` runes, owned by a small typed store module that encapsulates the lifecycle transitions (start, advance, clear, restart, etc.) and persists to Dexie. Derived values are `$derived`, never stored.

**Rationale.** Mirrors the data-model split: stored fields (roster, round, escalation, active pointer) vs derived (`sortedCombatants`, `escalationDie`, `canAdvance`, `healthStatus`). Runes are native, minimal, and keep the Setup→Active machine readable. The store layer is the single place transitions and persistence happen, so the undo/redo history and the "interrupted write" guard live in one seam.

**Alternatives.** Classic `writable`/`derived` stores (more boilerplate, pre-runes); XState (rigorous but heavy for a 2-state lifecycle).

**Consequences.** Undo/Redo is a **per-combat bounded history (10 deep)** owned by the store: before each reversible transition, a deep snapshot of the current state is pushed onto the stack, the header Undo ↶ / Redo ↷ walk it, and a new action clears the redo branch. The stack is persisted with the combat in Dexie (ADR-003) and dropped when the combat is deleted. Transitions are pure functions over state → easy to unit-test (ADR-009).

The store's top-level collections (`combats`, `libraryEntries`, `settings`) are `$state.raw`, not deeply-proxied `$state`: the store's contract is **replace, never mutate** — every transition, list edit and settings patch produces a new value and assigns it back, it never writes into an existing record. Nothing else needs deep reactivity because no component or controller ever binds to or mutates a store record in place; every `bind:value` in the app targets a component-local form `$state` instead. `$state.raw` also removes the need to `$state.snapshot()` store-owned state before handing it to a pure domain function or to Dexie — a plain, non-proxied value is already both. A snapshot is still required at the seam for values arriving from elsewhere (e.g. a caller-supplied patch built from a component's own `$state`), since those can still be live proxies.

Separately, the same HP transitions (including a Max-HP edit, pushed as its **own discrete undo step**) **append a read-only entry to that combatant's `hpLog`**. Because each snapshot carries the full `hpLog` at the time it was taken, undoing an HP action drops that entry for free (redo restores it) — one snapshot mechanism, no separate pop logic, and it is unit-testable alongside the transitions.
